# BOSS 直聘账号风控与自动化工具调研

核验日期：2026-11-09（Asia/Shanghai）。本记录区分官方公开规则、当前项目代码事实与工程建议，不推断未公开的检测模型或封号概率。

## 结论

BOSS 直聘《用户协议》明确限制未经许可的第三方工具接入、自动化获取信息，以及规避平台限制的行为，且直接列举爬虫和拟人程序。当前项目包含读取登录态、自动获取职位、自动浏览及自动发送消息的行为，因此存在明确的平台协议风险。随机延迟、拟人输入、使用自己的账号或附带免责声明，均不能据此视为取得平台许可。[S1]

本次查阅的官方公开资料没有提供求职自动化的安全访问频率、每日安全投递量、固定封禁阶梯或解封时间表，无法据此给出“不封号”的参数或概率。[S1][S2][S3]

## 官方明确规定了什么

### 未经许可的自动化工具

- 用户协议第四部分第 11 项：未经许可，不得通过第三方工具或运营平台获取平台内信息服务，列举登录、发布职位、浏览职位、收发简历。[S1]
- 用户协议第七部分第 5 项：限制未经许可通过插件、外挂、第三方工具等接入服务或系统获取信息，同时禁止规避平台流程、规则、功能限制或运营策略。[S1]
- 用户协议第七部分第 7 项：在其定义的未经许可获取信息情形中，直接列举“蜘蛛”、爬虫、“拟人程序”等非正常浏览手段。这里引用的是平台协议用语，不据此独立认定某个具体项目的法律责任。[S1]
- 招聘行为管理规范第 9.1 项还明确列举筛选匹配、定向推送消息、自动沟通等工具接入行为。该规范第 1.1 项将其用户定义为招聘者或有招聘需求的企业，不能把其中全部招聘端处罚细则直接套到求职者。[S3]

### 处置依据与可能后果

用户协议第八部分第 1 项规定，查实或有合理理由认为违反第七部分时，可删除或屏蔽信息、限制部分或全部功能，并可按紧急和严重程度不经事先通知暂停或终止服务。协议没有承诺先警告、再限制、最后封禁的固定顺序。[S1]

账号实际使用人与实名认证不一致时，用户协议第三部分第 3 项明确允许暂停、终止或永久禁用账号。不能把此项偷换为“每次脚本使用都会永久封禁”。[S1]

隐私政策第二部分（二）第 9(2) 项说明，账号或行为异常、违规触发风控时，可能要求姓名、身份证号、国家网络身份认证结果或证明材料，用于核验当前使用人身份。是否核验与是否处罚是不同问题。[S2]

招聘端另有冻结、资质核验、功能限制、教育警示及关联处置；重复或恶劣违规可加重处理。第八部分提供申诉复核，成立后撤销措施。这些详细分类属于招聘端规则，本文只作为平台公开治理方式的补充证据。[S3]

## 公开信息能支持的检测机制

隐私政策第二部分（二）第 9 项公开了以下安全用途：[S2]

| 信息或信号 | 政策中的用途与边界 |
| --- | --- |
| 账号、设备标识、IP、网络、设备及系统信息 | 用于安全运行、账号安全和异常排查；具体适用取决于终端、场景与授权 |
| 浏览、点击、查询、收藏、发布、分享，以及操作日期和时间 | 作为服务日志，用于预防恶意程序及保障运行质量 |
| 经授权的位置信息、操作行为 | 用于发现、定位和排查异常；招聘者另有人企关系核验场景 |
| 沟通记录、投诉、申诉及必要证明材料 | 用于投诉举报、申诉处理或安全风控问题 |

这些披露足以支持“风控会综合多个方面的信息”的判断，不足以证明其具体算法、权重或阈值。App 的进程信息、传感器、设备标识等披露也不能解释成普通 PC 网页拥有同等读取权限。

本次没有核实到官方公开以下内容：某种浏览器自动化框架是否必定被识别；某个请求频率必定触发处罚；验证码次数与封号之间的固定关系；短期限制的统一时长；随机鼠标、打字或滚动对封号率的实测影响。

## 如何理解异常状态

- 验证页面、身份核验、功能受限和账号暂停/终止应分别处理，不能仅凭一个错误页面推断永久封号。[S1][S2]
- 请求错误或超时也可能来自客户端或网络问题，官方 FAQ 提供了这类故障排查说明。[S5]
- HTTP 403/429 或业务错误需要结合响应和官方通知判定；程序应保守暂停，而不是将状态码直接标记成“账号已封”。此项为工程建议，不是 BOSS 公布的错误码映射。
- 发生限制时，应停止自动化，在官方客户端查看通知及核验/申诉入口，通过官方客服确认原因。官方使用帮助展示 APP“我的-我的客服”及电脑端“帮助反馈-在线客服”入口，但本次未查到求职者账号冻结的完整统一申诉流程。[S4]
- 隐私政策中“15 日内回复”用于相应隐私问题或权利请求，不能作为账号解封时限。[S2]

## 建议的优化顺序

以下为调研阶段提出的建议。第 1、2 项已在后续源码优化中部分落实，具体覆盖范围和剩余限制见文末；其余是后续方向：

1. 统一风险暂停：明确的访问受限、操作频繁、账号异常、验证码或身份核验信号，暂停全局检索、详情、发送及相关自动导航；保存进度，展示原始提示的脱敏摘要，等待用户通过官方页面处理并明确恢复。
2. 区分网络重试和平台拒绝：暂时性网络故障可有限重试；明确拒绝或限制不应进入普通自动重试，也不应自动切换关键词继续。
3. 增加人工确认发送：展示岗位、评分依据和招呼语后再由用户决定，发送状态不明时先核对已有会话。此改动减少误操作，不消除自动采集本身的平台协议风险。
4. 提供离线辅助路径：由用户导入有权处理的 JD、简历，在本地完成筛选和文案，最终在官方页面人工操作；或在取得明确授权后使用官方提供的接入方式。
5. 说明真实边界：文档和安装包不承诺“防封”“安全次数”或“拟人即可免检测”；免责声明仅说明风险，不能代替平台许可。

## 调研限制

- 本次仅访问官方公开页面、执行网页检索及只读源码核查，没有使用用户登录态访问平台，没有发送消息或实施封号阈值实验。
- 检索到的第三方脚本营销、经验贴、其他 AI 输出及非官方“代解封”页面未作为平台机制证据。
- 本次官方来源足以确定规则和公开数据类别，不能确定某一账号的当前状态、实际封禁概率或个案恢复时长。
- 调研阶段仅新增研究记录。其后的源码改动另记于文末，用户配置和已发布安装包未改动。

## 补充：用户提供的反调试文章核查

补充核验日期：2026-11-09。文章为 xirain 于 2026-02-22 发布的[《Boss 直聘反调试技术深度解析》](https://xirain.github.io/techlearn/posts/boss-zhipin-anti-debugging-analysis/)。本节为阅读与核查结论，不代表在 BOSS 生产页面上完成了检测复现。

### 文章的证据边界

文章介绍了快捷键拦截、对象属性/字符串转换探针、窗口尺寸、断点计时、控制台性能和第三方调试库识别。这些思路在通用前端反调试库中有实现依据，但作者对 BOSS 使用 `disable-devtool` 的判断明确使用了“大概率”一词。

该文没有附上能将这些具体检测器与 BOSS 当前部署关联起来的脚本 URL、文件哈希、抓取时间、浏览器版本和可复现实验记录。它链接了开源库，但没有给出“打开调试器 -> 服务端标记 -> 验证升级 -> 封号”的验证链。因此，应将其作为技术线索，而非 BOSS 封禁机制的确定说明。

### 对照一手资料的结果

| 文章表述 | 本次核查 | 结论 |
| --- | --- | --- |
| 库有 8 类检测器 | [上游检测器注册表](https://github.com/theajack/disable-devtool/blob/dee3f6334e6cdde3ceee0e9119c03aebcd4e2d81/src/detector/index.ts)确实列出 8 类 | 库能力可以确认，不能由此证明 BOSS 使用全部检测器 |
| 8 类检测器同时运行，每 200ms 轮询 | [上游配置源码](https://github.com/theajack/disable-devtool/blob/dee3f6334e6cdde3ceee0e9119c03aebcd4e2d81/src/utils/config.ts#L16)为 `interval: 500`，默认列表为 `[1,3,4,5,6,7]`；注释说明移除尺寸及正则探针与误触有关 | 不能将文章数字当成当前库默认值，更不能当成 BOSS 实际参数；调用方也能覆盖配置 |
| 无限 debugger 是所有浏览器上的核心检测方式 | [上游 Debugger 检测器](https://github.com/theajack/disable-devtool/blob/dee3f6334e6cdde3ceee0e9119c03aebcd4e2d81/src/detector/sub-detector/debugger.ts#L19)只在 `IS.iosChrome || IS.iosEdge` 时启用 | 文中的通用示例不等于该库在 PC Chrome 上的实际实现 |
| 控制台关闭时 console.log 是空操作，浏览器直接丢弃输出 | [WHATWG Console 标准的 Printer 部分](https://console.spec.whatwg.org/#printer)建议控制台未打开时缓冲日志，以便以后显示；格式化行为也依赖实现 | 不能泛化为“关闭即零开销”；参数表达式本身仍需执行，对象探针行为需要按浏览器和版本验证 |

| Token 代码每日变化、先刷新再升级验证码、通过某个 cookie 标记异常 | 文中没有提供可核验的部署或网络样本 | 本次保持未核实，不采纳为确证的账号处罚流程 |

### 对当前项目的实际含义

1. 应分别考虑前端反调试、自动化/请求环境异常和账号处置。三者可能有关联，但仅凭刷新或验证页不能确定触发了哪一种机制，更不能确定账号已经被封。
2. 当前项目通过 DrissionPage/CDP 操作浏览器，`boss_spider.py:206` 管理可见/无头模式。CDP 连接与用户打开可视 DevTools 面板不能直接等同；本次没有实测平台对当前工具链的识别行为。
3. 本项目 `boss_spider.py:100` 持久化选定的 UA，`:229` 注入脚本改写部分设备属性。这些实现本身不能证明浏览器环境一致或证明不会被识别。现有单元测试验证功能与调度，不验证反检测效果。
4. 页面异常反复刷新、正文突然消失或跳转验证页，值得作为暂停并让用户检查的信号。需要结合 URL、响应、页面提示和发生时间记录上下文，避免将网络故障或普通页面加载直接判成封号。这是工程建议，不是 BOSS 公布的处罚规则。
5. 文章不足以改变前文的优先级：先补全统一暂停、错误分类、进度保存和发送结果确认。本次没有加入文章中的绕过逻辑，也没有操作真实账号进行对抗测试。

## 本次源码优化

实施日期：2026-11-09。按用户“拟人操作不要过于刻意”的要求调整工作区源码，保留现有配置键和用户设置。

- 可见列表页每次只向下滚动一次，共用原有 60 秒冷却；去掉随机上下往返、连续微滚动与回到顶部。
- 后台模式不执行可选列表浏览；投递前不再额外滚动，输入不再逐字随机停顿。请求间隔、岗位间隔、详情页停留和数据懒加载所需滚动继续生效。
- HTTP 401/403/429、接口明确的频繁操作/受限/验证/登录失效提示及已知安全验证路由，触发整轮停止；不会自动重试受限请求或切换关键词继续。网络超时、服务端暂时故障仍有限重试。
- 主流程检查常见可见弹窗和提示条，避免将 JD 或聊天正文中的类似词句当成限制。验证页不会因出现头像而自动判为可继续。
- 停止时保存已完成的结果，退出心跳并关闭浏览器；面板显示“平台限制”，日志使用归类原因，不输出受限响应中的令牌或完整跳转地址。处理官方页面提示后，由用户手动重启。
- 去掉界面中“降低风控识别概率”的未经验证表述。未加入反调试绕过、验证码自动处理或新的指纹伪装。

验证：425 项测试、176 项子测试通过；临时 profile + 本地 HTTP 页面下的真实 Chromium 检查通过，包括正文/隐藏提示不误报、可见受限提示/已知验证路由会停止。命令和运行说明见 [runtime-heartbeat.md](runtime-heartbeat.md)。

边界：只覆盖当前实现的响应类别、路由和提示结构，不能保证识别所有页面变化。点击发送后出现限制时，消息是否被平台接收仍需人工核对；此优化没有实现完整的发送回执确认。没有真实账号实验，不能推断封号率变化。现有 v1.0.0 EXE、安装包和远端发行版尚未包含本次源码改动。
